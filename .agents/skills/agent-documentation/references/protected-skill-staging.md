# Protected skill staging

Use this workflow for every authorized change within a project-authored immediate `.agents/skills/<skill>` tree, including its `SKILL.md`, assets, references, scripts, adjacent tests, and durable fixtures. Keep read-only work unstaged. Do not apply this workflow to root `AGENTS.md`, `.agents/PROJECT.md`, or other `.agents` paths outside `skills`.

Zed’s native mutation tools force confirmation for a directly named or canonical path containing consecutive `.agents` and `skills` components. The [documented rationale](../../../PROJECT.md#protected-skill-staging) explains why the canonical skill layout remains unchanged.

- Create one task-specific `.agent-<name>` staging root at the current checkout’s root, outside `.agents/skills`. For every affected skill, preserve one immutable copy-time baseline and one editable copy of the complete `<skill>` directory at `<staging>/baseline/<skill>` and `<staging>/editable/<skill>`. Do not recreate `.agents/skills` beneath the staging root. For a new skill, preserve an explicit empty baseline and build the complete work-in-progress skill only under `<staging>/editable/<skill>`. Do not create its canonical `.agents/skills/<skill>` directory until reviewed promotion because Zed can discover and expose a partial skill to concurrent agent sessions. For a deleted skill, preserve the complete baseline and an explicit empty editable result. Apply this rule in the primary checkout and dedicated Git worktrees alike. Do not treat the worktree itself as the staged skill tree: its `.agents/skills` tree remains canonical and may be changed only during bounded promotion.
- Populate the immutable baseline from the canonical skill through normal native authorization, then create the editable copy from that unprotected baseline. Do not use terminal mutation, ancestor-directory operations, symlink indirection, or alternate path names to evade Zed’s sensitive-path confirmation.
- Make every iterative change within the editable skill tree. Run every focused check that can operate there, including applicable documentation, script, test, fixture, and human-facing copy validation. Because `.agent-*` staging roots are normally ignored, invoke ignore-aware formatters with an explicit override that includes the staged paths and verify that each intended file was matched. For Prettier checks beneath the staging root, pass `--ignore-path=/dev/null`; a successful zero-file check is not validation. Review the complete editable-tree diff against the immutable baseline before promotion.
- Recheck the status and diff of the canonical skill against the same baseline immediately before promotion. If the canonical tree changed after capture, keep the original baseline unchanged, capture one immutable snapshot of the new canonical state, and reconcile the original-baseline-to-editable task delta onto that snapshot with three-way semantics. Stop and report any unresolved conflict. Only after successful reconciliation, adopt the snapshot as the refreshed staged baseline, retain the reconciled editable tree, and review their complete diff. If the canonical tree changes again before promotion, stop and report rather than restarting the cycle or overwriting user or concurrent changes.
- Carry each finalized editable skill tree back to its canonical `.agents/skills/<skill>` destination with exact-tree semantics as one bounded promotion unit. The canonical result must match the reviewed editable tree, including intentional deletions. Do not use an additive merge that can retain stale files. Accept the native sensitive-path confirmation for this operation, and carry back only project-authored skill content—not scratch artifacts or build output.
- Verify the promoted canonical skill against the reviewed editable result, then remove both staged skill trees before repository-wide canonical validation so discovery cannot inspect duplicate sources. Keep only non-source evidence needed for the task. If correction is permitted, recreate one immutable baseline and one editable copy from the promoted canonical tree rather than retaining duplicate source trees through validation.
- Run the complete authoritative check set against the canonical tree in non-mutating check, dry-run, or inspection modes. Do not run a canonical validation mode that writes into the skill tree. If a required canonical-only check has no non-mutating mode, report the limitation rather than starting a write-and-promotion cycle. If validation discovers a staged duplicate, correct the validation setup and rerun once without treating that result as a skill failure or starting the corrective pass.
- Aggregate all canonical-only failures before correction. After the initial promotion, permit at most one corrective staged pass for canonical-only failures or path-dependent discrepancies, then perform one final promotion and rerun the complete authoritative check set. If validation still fails, the same discrepancy recurs, or another correction would be required, stop and report instead of cycling.
