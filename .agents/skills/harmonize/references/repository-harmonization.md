# Repository Harmonization

Run a change-oriented consistency pass by default. An explicit review or comparison request remains read-only. When the resolved scope includes agent documentation, follow `agent-documentation` and its [repository independence contract](../../../../skills/.domfiles-agent-documentation/references/repository-independence.md) for requirement selection, local ownership, shared wording, and new repository setup. Apply the global **Explicit user direction** policy to task-specific changes to this workflow.

Follow every repository’s instructions, disclosure boundary, concurrent work policy, protected-path workflow, and validation requirements. Don’t transfer private facts or secret-bearing values between repositories.

## Resolve Repositories

- **Scope:** Use Git repositories within the explicitly supplied project scope or location. Default discovery covers repository roots in immediate child directories of `~/Projects`, including hidden directories, the SSH project paths declared in [`ssh_connections` in the Zed settings](../../../../home/.config/zed/settings.json), and registered project roots in already linked remote environments exposed by available native or connected client interfaces, such as T3 Code. Default discovery neither recurses into local child directories nor scans remote filesystems beyond those project roots, and local client registrations don’t expand its local scope. Discovery alone doesn’t authorize linking environments, registering projects, or launching agents. Use the named concept, policy, or documentation family. Without a narrower content scope, compare project-authored agent documentation expressing shared policies, workflows, or terminology. Start from Git-tracked files and exclude agent task artifacts, generated files, managed files, third-party files, untracked files, and vendored files unless explicitly included. An authorized setup pass may create the necessary instruction surfaces.
- **Eligibility:** By default, discover repositories with tracked project-authored agent documentation and at least one configured Git remote pointing to `porada/*` or `standard-config/*`. A tracked `AGENTS.md` isn’t required. An explicitly selected repository may participate before it has agent documentation or a remote. Present the complete candidate list with stable repository numbers and distinguish source-only baselines from destinations. For a change-oriented pass, include the [current-branch pull](#update-selected-checkouts) in the candidate proposal, including for source-only baselines. An explicit user selection confirms its stated role and authorizes this pull for a change-oriented pass unless the user excludes the update. No separate pull confirmation is needed. Ask before further inventory, comparison, or mutation only when the repository set or any repository’s role remains unconfirmed. Don’t create files merely to satisfy discovery criteria.
- **Remote environment:** Assume in-scope SSH locations use domfiles with the same global agent instructions, globally installed skills, and managed command entrypoints as the local environment. Don’t extend that assumption to other environments merely because the client links them. Neither assumption nor linkage establishes remote access or matching host capabilities, and neither replaces destination repository instructions.
- **Remote discovery:** Use read-only operations for project listing and checkout eligibility checks, keeping SSH checks non-interactive. Environment reachability and project metadata identify possible locations, not verified repositories or filesystem access. Before including a remote repository as an eligible candidate, establish its checkout access and the facts required by **Eligibility** through bounded inspection. Before repository confirmation, inspect only what those checks require. Identify candidates by environment or SSH host, project path, and repository identity, retaining a configured display name where available. List inaccessible or otherwise unverified locations separately with the specific error or missing capability. Apply the same repository and role confirmation rules to every discovery source.
- **Remote access:** Select a supported, authorized route for each operation: direct client file access, commands through established SSH authentication, or an agent running at the destination under global **Host-managed execution**. Direct client file access and SSH commands may also perform authorized edits and validation when they supply the required tools and respect destination boundaries. Agent execution is a separate effect requiring covered execution and disclosure authority. Resolve uncovered effects through global **Execution checkpoints** before launching a discovery or execution agent. When an interface’s documented operations don’t include a required capability, use another supported, authorized route. Diagnose a failure from its returned error details rather than its error code alone. Treat authentication or permission denials under global **Retrieval failure**, without substituting a route to obtain the denied result.
- **Checkout boundary:** Preserve explicitly supplied checkout paths, including linked worktrees, rather than substituting a primary worktree. Resolve client projects from their environment, registered workspace, and repository identity, not a matching title. Verify the selected checkout before inventory or execution. Consolidate multiple discovery routes to the same verified checkout. For directory-based discovery and client project discovery, don’t expand through linked worktree registrations or inventory duplicate checkouts of one repository. When discovery finds multiple checkouts of one repository without an explicit selection, ask which to use during repository confirmation.
- **Inventory gate:** Before editing a destination, inventory its selected documentation family, check its working state and mutation feasibility, and read every applicable `AGENTS.md` and repository-specific authority model. Inspect the confirmed sources and related destinations needed to establish that change’s validity. Identify existing owners, supported client entrypoints, and any necessary new surfaces without expanding into a general repository audit. An unavailable destination may remain uninventoried and deferred when the planned changes are independently valid under [**Atomicity**](apply-harmonization.md#apply-changes). A required source or cross-repository dependency must still be checked before its dependent changes.
- **Baseline:** Use the explicitly selected baseline. Otherwise propose domfiles as the source-only baseline and obtain confirmation before inspecting it unless that role is already confirmed. A baseline doesn’t have to be a destination. Source-only confirmation permits bounded read-only comparison and the confirmed branch update, not other mutation. Apply the same checkout and access boundaries to it. Its global policies and authoring tools are source material, not prerequisites for destination collaborators.

## Update Selected Checkouts

After repository and role confirmation, pull each selected checkout’s current branch from its configured upstream before documentation inventory, comparison, or harmonization edits. This applies to source-only baselines as well as destinations. An explicitly read-only review or comparison doesn’t pull unless the user separately authorizes that update.

Before pulling, read the checkout’s applicable instructions and inspect its current branch, upstream, and working state. Use fast-forward-only integration with automatic stashing disabled, preserving the selected checkout and unrelated work under global **Concurrent work**. Don’t switch branches, choose a different upstream, create merge commits, or rebase to make the pull succeed. For remote checkouts, use **Remote access** with authority covering the update.

When no current branch or configured upstream exists, no pull applies: keep the selected checkout’s current state and report that limitation. If a pull fails or preserving current work prevents the update, defer its dependent work under [**Atomicity**](apply-harmonization.md#apply-changes) or obtain the user’s decision before proceeding from its current state. A required baseline must be available before its dependent comparisons. After a successful pull, reread applicable instructions changed by the update before continuing.

## Compare Requirements

- **Candidates:** Classify corresponding items using the shared wording rules below. When a confirmed baseline expresses an item that a destination lacks, treat that item as a candidate only when it may supply a required output property, not merely because the maintainer uses it. Treat an item the baseline doesn’t express as a consistency candidate only when at least two in-scope surfaces express the same observable meaning and role. Preserve intentionally different requirements. Ambiguous policy and general quality defects remain outside scope unless the named family explicitly includes them. Inspect implementation and tests only as bounded evidence needed to establish observable meaning.
- **Canonical form and placement:** Use the [shared wording rules](../../../../skills/.domfiles-agent-documentation/references/repository-independence.md#align-shared-wording) to select and reproduce equivalent formulations. Outside agent documentation, retain the applicable domain’s semantic owner and distribution model. Don’t resolve an unsettled acceptance requirement by silently copying the baseline or hoisting it into the maintainer’s global instructions.

A review-only pass records findings rather than applying changes.

## Validate and Report

Use `agent-documentation`’s validation workflow, including repository independence checks, for affected agent documentation. For other selected families, use the applicable domain checks and `git diff --check`. Re-read the complete compared family available within the authorized scope. Verify canonical correspondence across applied destinations and identify deferred destinations and remaining alignment gaps, without claiming complete alignment for a partial pass. Report the source and destination roles, changed repositories, canonical ownership, intentional variants, unresolved decisions, and material verification limits. Identify the compared revisions and whether each checkout was pulled, had no applicable pull, or was used without updating under read-only scope or explicit approval. Distinguish source-based checks from live client behavior. Don’t report discrepancies already resolved by the pass.
