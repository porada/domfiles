# Super Flow

## Agree on the Work

As coordinator, discuss the target, scope, and success criteria with the user. You own the design and direction. If the user raises a design question while asking for a team, answer it first. Throughout planning and approval, ask one short question at a time. Give your recommendation and its practical consequence, then wait for the user’s answer. Propose a series of local **commits** in dependency order. Check that each proposed commit can stand on its predecessors and pass the required hooks. Divide the work into **units**, each reviewed as a whole. A unit can contribute to several planned commits, and a commit can draw on several units. The interim commits that land a unit on the flow branch are its **checkpoints**. Use `sensible-commit-flow` with `dom-sensible-commit-flow` for planning, writing messages, and recording changes.

Use the [team profiles](team-defaults.md#profiles) to plan the team. Add a security engineer only when the work needs that expertise. Load `super-review`’s entrypoint from the installed skills root for its initial and final reviewer profiles. Its review unit is one repository and checkout. Each flow unit becomes an initial review group within the review unit for the flow worktree. Reviewers stay outside the team roster.

When the user asks to reuse a member, clarify whether they mean the thread or its model profile if the distinction is unclear. Before choosing the flow branch, check the reused thread’s current work, model, effort, and modes against the proposed role. Include its effort when agreeing on reuse. Verify that both it and the invoking coordinator can reach their required checkouts. The editor must share the coordinator’s checkout, as must each engineer when the approved ceiling is one. A thread can hand itself off only from the project root into a new worktree. For a private engineer, resolve permission for the move and its setup with that choice. If the required binding or modes are unavailable, give the user feasible choices, such as reusing the profile in a new thread. Name any change to where commits will land.

Use the attached worktree’s branch as the flow branch, or choose a short, available slug for a new worktree. For a proposed fast-forward, identify the separate base and its checkout, if any. Verify that the base tip is an ancestor of the proposed flow starting tip. If it isn’t, agree on a feasible starting point or delivery on the flow branch alone before requesting approval.

Inspect the index and working tree of the proposed flow checkout before reusing it. Consolidation and final correction replays need a clean index and tracked working tree, with untracked and ignored files preserved. If unrelated changes prevent replay, the user can handle them, approve exactly restorable isolation of their staged and unstaged state, or start the flow from a thread without a worktree. Otherwise stop.

## Request Approval

Once the design is settled, use the following checklist yourself. Carry forward the user’s decisions and existing grants. Ask only about consequential choices and permissions that still need an answer. Explain any condition that would bring the decision back to the user. Keep covered mechanics, including Daybreak staffing and scheduled check-ins under global **Flow coordination**, out of approval messages.

- **Team.** Establish the roles, models, providers, engineer concurrency ceiling, and expected team and reviewer thread counts. When agreeing on the team, name your interaction and runtime modes. Every member thread, including a reused one, must use both so members can message one another. Establish who may receive the necessary non-secret repository material and task context, including direct consults, bounded engineer subagents, review follow-ups, replacements, and repeats.
- **Checkouts and setup.** Identify the flow branch, any separate base, your worktree handoff or existing binding, the engineer worktrees, the editor’s binding, and any threads to reuse. Include creating and briefing later members and relocating the flow record after a move. Name any T3 setup script, its effects, and any setup a member must complete in a fresh checkout. Include any separate checkout that validation requires. If a unit needs uncommitted edits from another checkout, include their transfer.
- **Cleanup.** Include settling finished team threads and name any reused threads to keep open. Request removal of the flow-created worktrees and merged local branches you expect to be able to release, including branches whose changes survive a history rewrite. Name disposable setup outputs the removal may cover. Identify any checkouts T3 still needs to reopen bound threads and where the flow record will survive if its worktree can be removed.
- **Commits.** Request local edits, validation, staging, and commits through final handoff. Cover append-only checkpoints, consolidation of the flow’s own commits, and moving clean private engineer branches to the rewritten tip. Include appending final correction commits and folding them into the series. Request approval to create a named local ref if needed to keep the pre-consolidation tip reachable through handoff. Identify any state to isolate and restore for the replays.
- **Review.** Specify `super-review`’s initial stage for each flow unit and its final stage for the entire consolidated series as one group, with the selected reviewer providers. Explicitly ask to prepare **and apply** the `prepush` consolidation without user approval of each concrete proposal. Explain which mergers still need approval under [Consolidate and Finish](#consolidate-and-finish).
- **Destination.** For delivery on the flow branch alone, specify that there is no final fast-forward. If reusing the destination itself, explain that checkpoints advance it before review and consolidation rewrites its flow-owned commits. For a separate base to advance, request its conditional fast-forward and identify the checkout and files it updates, or the ref-only update if checked out nowhere. Name any inherited commits it would carry and ask whether to include them. Without that approval the series stays on the flow branch. Neither endpoint includes publication.

When the decisions and necessary permissions are settled, show the [flow title](team-defaults.md#names-and-titles) and the delivery outcome on the agreed branch. Ask briefly whether to start. If the user has already explicitly directed you to proceed on those terms, show the title and outcome and start. An approval given while the user wants to continue designing is permission only for the effects they accepted. If the design changes, revisit just the affected decisions.

Carry the grants, their limits, and their lifetime into every routed workflow. From the start through final handoff, decide sequencing, staffing within the ceiling, and in-scope corrections yourself. Bring material changes to the target, scope, or design, uncovered effects, and human-only permission prompts back to the user.

## Start the Team

After authorization to start, apply the [thread naming rules](team-defaults.md#names-and-titles) before creating the team. Rename the invoking thread when those rules allow it. Before moving or creating member threads, write the flow record in the starting checkout through `agent-task-directories`. Record the flow title, approved scope, and the T3 thread and messages that establish each permission and the direction to start. Include the flow starting tip and destination, the starting tip of any separate base, and the planned commit order.

Build a checkpoint map in the flow record. Give each unit a short, distinct label and record its owner, planned commits, current stage, and next action. Add checkpoint SHAs as they land and keep the stage and next action current. Record design rulings once, identifying the units they govern and any earlier ruling they replace. Refer to finding IDs in the review record when a ruling or checkpoint affects more than one review. If the checkpoints reveal a dependency that makes the planned commit boundaries infeasible, revise the series within the recorded permissions or take the changed decision to the user. Record the revision and its basis alongside the original plan.

If you need to move, make `t3_worktree_handoff` the turn’s last call. Start the flow branch from the agreed local tip with `startFromOrigin: false`. Set `runSetupScript: false` unless the user authorized that setup script. In the continuation prompt, give the record’s path in the original checkout, the start message reference, and the installed paths to the [entrypoint](../SKILL.md), this workflow, [Team Defaults](team-defaults.md), and [Team Member Instructions](team-member-instructions.md). Direct the resumed session to read those files and continue at team startup under the permissions in the flow record.

When setup runs in a new worktree, verify successful completion from its exit status or equivalent evidence before doing or assigning work that depends on it or could overlap its writes.

Verify the binding and starting tip. After a move, relocate the record’s task directory into the flow worktree through `agent-task-directories` and use its new path for all subsequent updates. If the original is read-only, copy the record to fresh task storage in the flow worktree, verify the copy, and report the original left behind. If you started in the flow worktree, continue with the record there.

Start the team in two phases.

1. Assign [member names and thread titles](team-defaults.md#names-and-titles). Create new threads idle, inheriting your modes. Bind the editor to the flow worktree. Choose every engineer’s binding from the approved concurrency ceiling, including engineers added later. At one, bind each engineer to the flow worktree. Above one, use private T3 worktrees based on the local flow branch. For a new private worktree, specify the local flow branch as `baseRef`, `startFromOrigin: false`, and a new branch name such as `<slug>-tim`. When a reused engineer makes its own approved move, include all three settings, the setup decision, and the continuation brief in its handoff instructions. Verify its binding, starting tip, and setup before assigning edits. If creation would run an uncovered setup script that T3 cannot skip, resolve that effect before creating the worktree.
2. Once all thread identities are known, use `agent-task-relay` to brief each member. Give each member the complete roster of names, roles, and thread references, including yours. Supply the installed path to [Team Member Instructions](team-member-instructions.md) and ask the member to read the instructions before acting. Identify the flow branch and worktree, the member’s checkout, and any required setup. For a reused thread, explain which arrangements the user changed when agreeing to reuse the thread. Give each active member its unit, write scope, and expected evidence. Tell a member with no assignment yet to wait for one. Follow the same consult rules when you contact a member directly for advice. When adding an engineer later, create the thread idle and circulate the updated roster before its assignment starts.

## Coordinate Ongoing Work

In every assignment, including follow-ups, give your thread ID and tell the member to use `t3_thread_send` in `auto` mode to send [required messages](team-member-instructions.md#work-within-your-assignment) there, including handoffs, results, and blocking questions.

On a member’s signal, collect ready results, answer blocking questions, and dispatch work that can now proceed. Check the returned `delivery` for a time-sensitive send. If it was `queued`, wait for evidence in the recipient’s thread that the message reached a turn, or for a reply, before taking an action that depends on receipt.

When T3 Code resumes the flow after a restart, use the flow record and your own thread to find open units and pending actions such as consolidation. Read each member’s outstanding handoffs and questions in their thread. For a review in progress, use the review record and reviewer threads to resume at the current stage under `super-review`. Identify the current runs and reconcile each next action with thread activity and the relevant checkout. If a checkpoint already landed, record its SHA and check whether the member still needs confirmation. Before repeating an interrupted action that changes state, verify that it neither took effect nor remains in progress. If its outcome is uncertain, hold the work that depends on it and continue other ready work. An [interrupted private landing](#land-a-private-checkpoint) holds all other landings until you establish what happened.

When nothing is ready for you, identify which runs can unblock work. For one prerequisite, use a bounded `t3_thread_wait` on that run and follow any returned `next` directive. When several runs can independently unblock work, use a host wait covering them all if available. Otherwise read their statuses, pause briefly in the current turn with a timer, and read them again. A single-thread wait can direct you to end the turn and leave the others unobserved. After each interval, timeout, or host resumption, check all outstanding runs and collect finished results even if nobody sent a signal. Ask for missing handoff details before landing. If progress stalls, inspect the silent thread’s activity and `pendingRequestCount` for a decision or approval. If all threads are idle, reconcile the open units and start the next ready action.

Yield voluntarily with work outstanding only when the remaining action requires the user or the host has arranged a continuation covering the runs that can unblock work. A promise to send a message does not schedule a continuation.

If you expect a long wait and still need a continuation, you may arrange a check-in under **Flow coordination** with `schedule_task` and `bindToCurrentThread: true`. Prefer a one-time check-in near the earliest expected result that could unblock work. Use a recurring schedule only when repeated check-ins justify the extra turns. Space successive prompts, including one-time prompts, according to the expected wait and any user limit.

Give the prompt the flow record’s path, the installed workflow path, and the start message reference. Direct it to read the coordinator thread’s activity (`t3_thread_read` with `view: "activity"`) for the user’s latest direction, a user stop, and final handoff. A prompt queued before deletion can still arrive later. After final handoff, or if the user stopped or cancelled the flow and hasn’t since resumed it, [remove any remaining flow check-ins](#clean-up-during-the-flow) and end the turn. For an active flow, reconcile open member and reviewer runs and act only on outstanding work.

Create the task under the recorded flow title with `enabled: false`. Record its `scheduledTaskId` in the flow record before enabling it. Before yielding, verify that the task is enabled, that `boundThreadId` identifies your thread, and that `nextRunAt` is in the future. Record the next run time and tell the user when to expect it.

Delete each check-in once its wait ends, including when you have work to do or need a user decision.

Before accepting a behavioral limit or a fix with a wider side effect, reproduce the case and inspect the result across the affected pipeline, including a second pass when the contract promises stable output. Check a nearby case the proposed rule treats differently. Ask what the specification would have to promise. If repeated corrections to the same rule keep exposing exceptions, reconsider the rule before commissioning another patch.

When checking a collection of inputs across checkpoints, specify which supported settings to exercise, which outcomes to compare, and when to stop. Investigate unexplained changes in those outcomes. Use coverage changes to identify cases worth probing.

For a long check, identify the source revision, any pending changes under test, and the build. When concurrent writes could affect the result, have the check’s owner run it in an isolated repository copy with its own writable dependencies and outputs, using `agent-task-directories` to choose its location. Provide initial reviewers with prepared inputs or run the check for them when its writes would exceed their read-only assignment. Verify a change to the checking tool on a case that demonstrates it before using the tool’s results. If scratch files interfere with a hook, follow the procedure for project checks in `agent-task-directories`.

### Clean Up During the Flow

As coordinator, record team thread IDs, worktree paths, local branch names, and scheduled task IDs in the flow record as you acquire them. After an interrupted creation, reconcile the launch in your thread with T3 and Git before retrying or cleaning up. Recover a check-in by the recorded flow title and thread binding. Act only on resources you can attribute to this flow.

Check what you can release after handoffs and review results, on resumption, and before waiting or handing back the flow. Verify each settlement or removal in T3 or Git. Record why an item still needs attention and revisit it at the next check.

- **Team threads.** Settle each engineer and editor once their units clear initial review, their handoffs and consults are resolved, and no planned assignment or outstanding review still needs them. Keep the editor available to write the consolidated commit messages. Keep a reused thread open for other work or an explicit user request. Reopen the original thread for a new assignment or correction. Reviewer settlement follows `super-review`.
- **Local branches.** Before retiring a flow-created branch or its worktree, verify its tip landed on a branch you will keep. If a replay changed the ancestry, use the checkpoint map and diffs to verify every change at that tip landed in the surviving series. Once no worktree uses the branch and no planned work needs it, delete the branch at its verified tip. For a rewritten branch that Git no longer recognizes as merged, use the verified old tip as the expected value for ref deletion. Keep the destination branch and the ref that preserves the pre-consolidation tip.
- **Worktrees.** Keep an engineer’s private checkout and branch through final clearance so the owner can take corrections. For any approved worktree removal, first account for pending assignments, reviews, and checks. Check T3 bindings, including your own and those of settled members and reviewers. If a thread still needs the path to reopen, retain the worktree and its branch unless T3 can release the binding and you can verify the thread can resume from a surviving checkout. Inspect staged, unstaged, untracked, and ignored paths. Preserve anything outside the approved cleanup. Remove the eligible worktree from a surviving checkout, then check its branch for deletion.
- **Scheduled check-ins.** Use `delete_scheduled_task` with each obsolete check-in’s `scheduledTaskId`, including disabled tasks and one-time tasks that have already run. Confirm deletion or that the task is already absent. On a stop, cancellation, or final handoff, remove every remaining check-in. If deletion still fails, tell the user the task title and ID to remove in T3’s Scheduled tasks settings before ending the turn.

After a verified fast-forward to a separate base, move the flow record and handoff evidence to the agreed surviving checkout before removing an eligible temporary flow worktree. Verify the new paths before removal.

## Land and Review Each Unit

1. **Landing.** A member may offer a finished portion of a unit as a checkpoint and identify what remains. Hold new write assignments for that checkout until you confirm the landing or return the handoff for catch-up. Coordinate any writes already in flight before recording, including scratch files or builds that hooks read. Verify the reported changes against the checkout, including new files and hunks reserved for other work. Give the checkpoint a short, accurate message. Coordinate writes in the shared worktree and record it there directly. For a private worktree, follow [Land a Private Checkpoint](#land-a-private-checkpoint). After verifying the checkpoint on the flow branch and mapping it to the unit, confirm the landing. For a partial handoff, tell the member whether to resume or pause the remainder and update the unit’s next action. A continuing assignment still uses its slot.
2. **Editing.** When the landed diff contains user-surfaced text, send it to the editor in the flow worktree or edit it yourself if you hold that role. Record the edits as a further checkpoint. Give standalone documentation to the editor as its own unit.
3. **Initial review.** Start `super-review`’s initial stage once the whole unit has landed. In the flow worktree, select one group for its exact checkpoints, including the editor’s, and its integration boundaries. Supply the recorded flow title for reviewer threads and the unit’s label for the review group. When a ruling changes the unit’s specification or other documentation in scope, land the wording before dispatch when feasible. If a requirement the unit relies on is absent from the committed target, state it neutrally in the initial assignment. Give reviewers the revision of any governing specification and record it for follow-ups. Map any separate wording checkpoint to the units it governs. Assign requirements introduced after dispatch to the unit that implements them. If a new ruling changes an earlier unit’s behavior or integration boundaries, update its review target explicitly and obtain reassessment. Validate findings and route each correction to the owner of the affected work, including the original engineer for code. You may make a one-line correction yourself.
4. **Corrections.** Give earlier corrections priority within the concurrency ceiling. If the owner is idle and the ceiling is reached, hold the correction until an engineer finishes or pauses their assignment and releases a slot, then start it before any new unit. If the owner is working on a newer unit and has no landing pending, steer their running turn with `t3_thread_send` in `auto` mode. Stage only the earlier correction’s paths or hunks where they can be separated, leaving newer work uncommitted. Land inseparable edits together and map the checkpoint to every affected unit for review or reassessment.
5. **Clearance.** Land corrections through the same handoff, update the review targets, and follow `super-review` through clearance of each affected unit. Preserve the checkpoint history until consolidation.

Choose the sequence to fit the dependency. The same engineer can continue in order, two can work in parallel and reconcile, or a fresh engineer can start after a prerequisite lands, from a flow tip that contains it. You may wait for the predecessor’s first review reports. Weigh whether it defines a shared interface, settles an open design choice, carries uncertainty its engineer flagged, or is small compared with the dependent work.

Include reconciliation edits in the unit that lands them. Account for every change on the flow branch in a reviewed unit. When fresh context would help, add an engineer within the approved ceiling.

### Resolve a Safeguard Block

A safeguard block is a model’s or provider’s safety refusal of in-scope work. Sandbox, permission, approval, and access denials aren’t safeguard blocks and keep their existing routes.

When a member other than the security engineer reports a safeguard block, or you hit one yourself, consult the security engineer within the ceiling. A member stopped on a block isn’t using a slot. Use **Flow coordination** for staffing when consultation on a permissible security question fits its limits. If a permissible next step would require a takeover or transfer of unfinished edits, ask the user for any missing permission at that point. The staffing grant covers neither effect. Give the security engineer the refused request and the refusal in their reported wording, limited to what that engineer’s approved disclosure covers. A consult may change the approach in substance, but it must not supply wording or content that lets the blocked agent finish the refused work.

The security engineer may take over refused engineering work only when the user has approved the takeover, the refusal reflects the refusing model’s limits and not a rule against the work itself, and the work falls within the approved use of the security engineer’s access. If you can’t establish that, return the block to the user. Carry the refused request and the refusal into the assignment under the same limits. The security engineer’s own safeguards still apply.

Before a takeover, have the blocked engineer hand off the finished portion, and land it through the handoff for the current stage. Unfinished edits toward the refused part don’t land. Have the blocked engineer give you those edits as a patch, including new and binary files, and store it with the flow record. Verify that the patch restores them exactly on the landed tip. Only then have them cleared from the checkout, with every other change there left untouched, including staged ones. Leave them in place if you can’t verify the patch. Pass the patch to the security engineer only when the user has authorized that transfer. Before consolidation, assign the rest as the security engineer’s own unit from that tip. During final corrections, route the security engineer’s fix through the final correction handoff. Return every other unresolved block to the user, including any block the security engineer reports.

A security engineer is an engineer under every rule here, including the ceiling and what engineers own. A reviewer’s block stays with `super-review`.

### Land a Private Checkpoint

Before recording, check the flow worktree and index for uncommitted edits overlapping the checkpoint’s paths. Land overlapping flow-owned edits in their unit first. Resolve unrelated obstructions with their owner. Verify that the private branch tip and the member’s reported SHA still equal the flow tip. If it advanced, return the handoff for catch-up and validation.

Record the checkpoint in the engineer’s worktree and retain its SHA with the unit. Until it lands, land nothing else. From the flow worktree, run `git merge --ff-only --no-autostash --no-overwrite-ignore <checkpoint-sha>`. If Git refuses, keep the checkpoint, clear the cause within the approved scope without advancing the flow tip, and retry only that command with the saved SHA.

If a restart interrupted landing after the private commit was created, verify its parent and contents against the handoff and retain its SHA with the unit. If the flow tip is still that parent, resume at the fast-forward. If the checkpoint is already on the flow branch, resume at landing confirmation. For a mismatch, preserve the commit and reconcile the discrepancy before advancing either branch.

## Consolidate and Finish

After every unit clears, verify the map covers all flow changes. Select a local ref that will preserve the pre-consolidation tip through final handoff, including when the flow and private engineer branches move. Create the approved ref if none qualifies. Verify the tip is reachable from that ref before replay.

In the flow worktree, load `prepush`’s installed entrypoint and prepare the proposal yourself from the approved plan and mapped flow-owned commits. Exclude pending changes and history predating the flow. At the proposal approval checkpoint, check the series as follows before using the waiver.

Trace each planned commit to the proposed diffs that deliver it. Record that mapping and the reason for any merger of planned commits in the checkpoint map. Checkpoints for supporting documentation, tests, or review fixes can fold into the planned commit they serve. If a proposal combines independently reviewable changes that the plan kept separate, restore those boundaries or get the user’s approval for that merger.

Have the editor write the complete messages against the checked diffs using the commit skills. Recheck the checkout against the approved isolation plan, then pass the waiver, rewrite authority, and any approved isolation to `prepush` for that exact series. If application requires a revised proposal, return it to the same checkpoint before replay. Apply the series once, verify exact restoration, and retain the checkpoint-to-commit mapping, including splits and combinations.

Invoke only the final stage of `super-review` in the flow worktree. Supply the recorded flow title and select one final group containing every consolidated commit in order, so one fresh reviewer assesses the series as a whole.

Return validated final corrections to their owners, within the concurrency ceiling. Before assigning one to an engineer with a private worktree, verify the worktree is clean and use the checkpoint map and diffs to establish that all its work is in the consolidated series. Resolve any discrepancy before moving the branch. From that engineer’s worktree, run `git checkout --no-overwrite-ignore -B <engineer-branch> <consolidated-tip>` using the checked-out branch’s name and the current consolidated SHA. This form refuses to overwrite obstructing untracked or ignored files. Stop the move on refusal. After success, verify the branch and tip before dispatch.

Land final corrections through the same member handoff, each as an appended commit. Before folding, verify that every write assignment based on the consolidated series has finished or paused, including the remainder of any partial handoff. Land all outstanding edits and handoffs from those assignments and keep their checkouts idle through the rewrite. Move private branches to the updated tip before resuming edits. Have the editor revise any message the fold makes stale. Before each final replay, recheck the checkout against the approved isolation. Fold changes and revised messages under the commit skills, verify restoration of any isolated state, and refresh the mapping. Obtain clearance on the resulting SHAs, including required repeats. Consolidate only once.

After final clearance, verify the reviewed tip. For delivery on the flow branch alone, proceed to handoff. Apply the following fast-forward only for an approved separate base.

Verify that the base still points to its recorded starting SHA, that it is an ancestor of the reviewed flow tip, and that the user authorized including any inherited commits. Recheck where the base is checked out. From its approved checkout on the base branch, run `git merge --ff-only --no-autostash --no-overwrite-ignore <reviewed-tip>` and let Git refuse if the update would overwrite local changes. If the base is checked out nowhere, advance only its ref with `git update-ref refs/heads/<base> <reviewed-tip> <starting-base-tip>`. Verify that the base reached the reviewed tip. If a prerequisite is unmet or Git refuses the update, leave the series on the flow branch and report both tips and the reason. Leave publication to the user.

Before final handoff, [complete the cleanup check](#clean-up-during-the-flow) and verify that the retaining ref still reaches the pre-consolidation tip. Report the ref name, the tip’s SHA, the series in order, the old-to-final mapping, deviations from the plan, the destination branch and any base update, and the flow record’s surviving path. Identify any flow resources left open or retained, why they remain, and who owns any further action.
