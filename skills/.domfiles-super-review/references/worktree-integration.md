# Worktree Integration

## Choose the Local Destination

The outermost super command owns integration. Honor the user’s selected destination. A read-only review or one limited to uncommitted changes finishes in the task worktree. For a standalone `super-review` in a linked worktree with a committed result planned and no destination selected, finish on the task branch if the task has a planned or linked pull request or the branch heads an open one. Otherwise fast-forward the local primary branch.

For the pull request check, inspect the task and thread, then check for an open pull request on the intended upstream using the task branch and its head repository. The branch’s tracking configuration can help identify that repository. Identify the primary branch from project policy or the intended upstream’s verified default branch. Resolve ambiguous matches or conflicting destinations with the user.

For a separate base, record its branch, starting commit, and any worktree holding that branch. Apply the invoking workflow’s grant for replay and fast-forward to the user-selected or default local destination. Verify it covers every incoming commit, including inherited work. At startup, [check the base against the proposed task tip](#reconcile-with-the-local-base), accounting for planned commits. Keep commits already reachable from the base intact when preparing or correcting the series. Record the destination and affected paths with the unit’s review target, using the planned paths for pending work. Treat commits already accepted on the base’s verified upstream, or another baseline the user selected, as comparison history. Cover the remaining incoming commits, including unpublished inherited work and its interactions with the task. Reuse applicable clearance and obtain any remaining coverage within the approved scope.

## Reconcile With the Local Base

When task-owned pending edits prevent a replay or a fast-forward of the task branch, defer that update. Continue reviewing or preparing those edits under the invoking workflow. Once they are committed under its authority, recheck ancestry and reconcile. In a standalone review, do so before cold review dispatch, or before landing after a peer-only review. Leave unrelated changes in place and resolve any obstruction with their owner.

If the base can fast-forward to the candidate or already contains the complete intended result, proceed. If the task tip is an ancestor of the base and more task commits are planned, first fast-forward the task branch to the base with the [checked-out branch safeguards](#land-the-reviewed-commit). When the base and candidate have diverged, identify where the task branch left the base. Use the base’s reflog to establish the fork point when its history was rewritten, so the replay excludes superseded base commits. Retain the result on the task branch and report the reason if the fork point is uncertain, any commit to replay falls outside the task, or the full range fails **Rewrite eligibility** or **History coordination**.

In the task worktree, use the history-update route in `sensible-commit-flow` with `dom-sensible-commit-flow` for a base-only update, including the personal overlay’s **Corrections and History Updates** rule for flow delivery refs. Starting at the fork point, replay onto the current base tip only the task’s eligible unpublished commits that the base lacks. Resolve a conflict there when the resolution preserves both changes’ intent. If it requires choosing between the changes or altering another task’s landed work, retain the result on the task branch and bring the decision to the user. For any other Git refusal, retain the task branch and report both tips and the reason.

After a replay, match each reviewed commit to its successor. Carry its review coverage forward when its patch is unchanged, intervening base commits left its paths untouched, and the evidence still covers its integration boundaries under **Validation evidence**. Include changes removed by a base rewrite in that comparison. Treat a conflict resolution as a changed commit. Rerun validation the new base could affect. Where coverage cannot carry forward, return the affected commits and their interactions to the existing reviewers through the selected stages. For a cold review in progress or already cleared, follow `cold-review`’s **Continue After Changes**.

## Check the Candidate Before Cold Review

Before dispatching cold review for a local integration, [check the candidate against the current base](#reconcile-with-the-local-base). If the base differs from its recorded tip, recheck the approved range, checkout, and validation. Verify it can fast-forward to the resulting candidate or already contains it. Record the verified base tip for landing. If a checkout would change, verify its binding, inspect its scoped status and diff, and check incoming paths for obstructions, including untracked or ignored files. Raise any obstruction with its owner. Continue review in the task worktree while a checkout-only obstruction holds landing. Run the review against the resulting commits in the task worktree. Keep the destination and these checks in the coordinator’s record. Use the existing `cold-review` prompt and reviewer lifecycle.

## Land the Reviewed Commit

After the selected stages clear, verify that the exact candidate contains every selected change, including pending edits from a peer-only review. Record those edits under existing commit authority and confirm that clearance still covers the result. If the complete result cannot be committed or covered, report the worktree result and hold the base update. Recheck the destination branch, checkout, ancestry, affected paths, and review coverage against the agreed update. If the base already contains the cleared tip, integration is complete. Otherwise [check the candidate against the current base](#reconcile-with-the-local-base). If the base moved, recheck the range and checkout and use the resulting cleared commit for landing. Preserve newer task-branch commits outside the update.

From the verified checkout on the base branch, run `git merge --ff-only --no-autostash --no-overwrite-ignore <cleared-tip>`. If the base appears checked out nowhere, recheck worktree use immediately before a ref-only landing. If a worktree holds the branch, including during an operation with a detached `HEAD`, keep the candidate on the task branch until landing can proceed. Only when the base is unused, run `git update-ref refs/heads/<base> <cleared-tip> <expected-base-tip>`. Verify the resulting tip and scoped checkout status and diff. A fast-forward to the exact cleared commit preserves its review coverage. If the checkout binding has changed outside the approved effects or Git refuses the landing, retain the result on the task branch and report both tips and the reason.
