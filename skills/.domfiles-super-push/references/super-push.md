# Super Push

## Identify the Outgoing Commits

Start with the invoking agent’s task, including its uncommitted work. If the task spans repositories, establish which one the user intends to publish. Preserve review dependencies across repositories.

At startup, check the task and thread for a planned or linked pull request and check whether the task branch heads an open pull request on the intended upstream. Use the branch’s tracking configuration to help identify its head repository. A tracking branch alone does not select a publication destination. Default to publishing the repository’s primary branch, including from a linked task worktree, when the task has no pull request and the user has selected no other branch. Identify the primary branch from project policy or the verified default branch of the intended upstream. Locate its local checkout, if any, and resolve the remote destination from the primary branch’s push configuration. Follow the installed `super-review` skill’s `references/worktree-integration.md` to record the local destination under global **Push preparation grant**. Resolve ambiguity before publication.

Publish the task branch in any checkout when the user explicitly requests that branch or it is the verified head for the task’s planned or existing pull request. Resolve conflicting destinations or ambiguous pull request matches with the user. Resolve its destination from the request and that branch’s push configuration, or verify the pull request’s head repository and branch separately from its base. Deliver on the selected branch and leave the primary branch in place. Preserve contribution approval requirements, explicit local-only limits, and any selected destination.

Verify that the push reaches one authorized endpoint. Use that endpoint for destination checks, including when the remote has a different fetch URL. If the destination is ambiguous or the remote would push to several endpoints, resolve the intended one before publication. Record whether the destination branch exists. Advance an existing branch by fast-forward. For a new branch, establish the comparison base for the outgoing series, using the verified pull request base when applicable. Obtain approval for branch creation if the publication grant does not already cover it. Continue independent review work while publication approval is pending.

Before reconciliation, identify the last commit needed to deliver the invoking task and select it by default. If the user selects all unpushed commits, select the current local branch tip even when it includes later work from other tasks. If pending task edits must be committed for the update, record them under **Push preparation grant** and identify the selected tip including the task’s intended changes before replay.

For committed delivery on a separate local base, reconcile the whole task branch under the shared procedure, including its ownership and eligibility checks for the full replay range. Through preparation and landing, if a replay or rewrite replaces the selected tip, use the verified successor ending the selected work. The outgoing range includes every commit that endpoint would add to the destination, including unpublished commits inherited from the base. Use that range for `prepush` and review.

Check publication readiness for every outgoing commit, including the selected tip. In T3 Code, use relevant task and reviewer threads to identify the work, prior clearance, and any hold on publication. Reuse clearance that still covers the commits and their interactions under **Validation evidence**. An open or settled thread alone establishes neither readiness nor a hold. Include commits lacking applicable clearance in this review, even when they originated outside T3.

Respect explicit exclusions, outstanding findings, and work another agent is actively revising. Resolve findings within scope. When a correction needs coordination with another task’s owner, use an already authorized channel or bring the decision to the user. If an outgoing commit must stay local, continue independent review work and report what still prevents the push.

## Review and Prepare the Series

Read and apply `super-review`’s entrypoint from the same installed skills root. Pass it the task worktree, resolved review target, local integration plan, and authority from **Review workflow requests**. Use its default review stages unless the user selects otherwise. An explicit read-only or local-only limit applies throughout.

Run `prepush` from its installed entrypoint when preparing commits for cold review, including when the user skips peer reviews. If publication is in scope and the user omits cold review, run `prepush` before peer reviews start. Inspect the diff and message of every outgoing commit, including commits from other tasks, along with the invoking task’s eligible pending changes. Reuse applicable assessments under **Validation evidence** and reassess any grouping or message affected by later corrections.

Pass the proposal waiver and local rewrite authority from **Push preparation grant** to `prepush`. Limit proposed changes to the invoking task’s eligible unpublished commits and pending changes. Pass any separate local destination as a protected ref. Preserve commits it already contains, including unpublished ones. Keep affected commits as they are wherever a rewrite would require replaying another task’s commits or setting aside unrelated changes without authority.

Hold the push while any outgoing commit’s subject starts with an autosquash marker (`amend!`, `fixup!`, or `squash!` followed by a space), even if that commit has review clearance. Fold it into its verified target when the rewrite is authorized. If the verified target is already published and an ordinary follow-up commit preserves the intended correction, record it that way when authorized. For each remaining marker, report the commit, its intended target or the ambiguity, and the decision or coordination needed to resolve it.

Review the resulting task commits. For every other commit in the selected outgoing range, obtain any stage coverage still needed for that commit or its interactions. Reassess any coverage affected by a revised series.

## Push the Reviewed Tip

After the selected review clears, identify the exact reviewed tip containing the task’s intended changes. A review limited to uncommitted changes ends at the local result. If newer work descends from the reviewed tip, push only through that tip. If the local branch has lost the reviewed tip, establish which commits still belong to the task and refresh affected clearance.

Refresh the remote destination before updating a separate local base. If the local base moved, reconcile under the shared procedure before comparing the resulting candidate with the remote. If an existing remote destination has disappeared or diverged, retain the candidate on its task branch. Recompute the range through the selected tip or its successor. Start from the refreshed remote destination, or from the verified comparison base for an authorized new branch. Return newly exposed commits to the readiness, `prepush`, and review steps above. Verify that clearance covers every outgoing commit and its interactions and that the range is free of autosquash markers.

Complete agreed local integration through the shared procedure, including when the remote already contains the reviewed tip. If the base moves again at landing, repeat the outgoing range and readiness checks for the resulting cleared tip. If local landing cannot complete, retain the candidate on the task branch and report the obstruction. Once it lands, push that cleared commit if the remote still lacks it.

Show the destination and the complete outgoing commit messages before pushing, reusing any messages already shown for those commits. Under **Git publication**, push the reviewed object ID to the explicit branch ref. Require the remote ref to still point to the commit used for the verified fast-forward, or to still be absent for authorized creation. If its state changes, repeat the destination and coverage checks. If the push is refused, retain the local landing and report the local and remote tips with the reason. Limit publication to that branch even when Git is configured to push other refs, tags, or submodules. Verify the destination contains the reviewed tip before reporting publication. When the run included cold review, apply `super-review`’s coordinating thread settlement rules at this workflow’s final handoff.
