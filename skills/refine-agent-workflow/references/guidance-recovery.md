# Guidance Recovery

Determine whether the affected guidance is required. A missing local target, a malformed destination, an HTTP response reporting the resource as missing or permanently unavailable, or a verified conflict with current behavior indicates defective guidance. Access restrictions, authentication problems, network failures, and HTTP server errors alone don’t establish a defect. Report verified defects with evidence and recommend updating the skill.

When required guidance is defective, use a complete available fallback or verify a replacement against authoritative evidence. Don’t substitute an unverified location. Ask before changing an explicitly selected version or another material task assumption. Problems with optional or supporting guidance don’t stop the workflow.

For retrieval failures that don’t establish a defect, correct a demonstrated path or invocation mistake, make bounded retries, or use an equivalent method. Keep the target, authorized effects, authentication, and disclosure boundaries unchanged. Use the supported grant or correction process for access restrictions.

When recovery cannot proceed, report the affected resource, attempted methods, failure evidence including the exact error when available, and smallest corrective action. Continue only independent authorized work. A procedural waiver doesn’t supply missing evidence or establish that an omitted or failed step succeeded.
