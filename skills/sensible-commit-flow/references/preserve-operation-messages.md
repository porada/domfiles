# Preserve Operation Messages

1. Resolve the repository, destination checkout and branch, source commits, and operation order. For a named merge source, retain both its name and resolved commit ID. Record the destination’s starting `HEAD`, inspect the source patches and complete messages against the relevant destination history, and identify unrelated index and working tree state to preserve. Don’t substitute the destination’s uncommitted diff for the operation’s changes or proceed through an unrelated Git operation already in progress.
2. Preserve complete inherited cherry-pick messages and Git-generated merge messages by default, including bodies and trailers. Skip hunk grouping, and don’t apply message composition or authored message conventions to inherited or generated messages. Resolve an explicit message rewrite request during preparation rather than silently normalizing the existing message. If the request requires composing replacement wording, load [Compose Messages](compose-messages.md).
3. Add the exact operation and invocation, any source names and commit IDs in operation order, destination and starting `HEAD`, intended changes, and expected parent relationships to the shared [execution baseline](commit-execution.md#confirm-commits). Identify inherited messages by their inspected source commits. For generated messages, retain a read-only preview when available or record the inputs from which Git will generate the message instead of inventing exact text. When shared confirmation requires presentation, put each complete inherited message or available generated preview in a blockquote without rewriting it, and otherwise state that Git will generate the message from the approved inputs.
4. During [Create Approved Commits](commit-execution.md#create-approved-commits), use the operation’s native preparation, command, and continuation flow rather than staging authored hunk groups or replacing it with freshly composed commits. For a named merge source, verify that it still resolves to the recorded commit ID and use the name as the merge target so Git retains ordinary branch provenance in its generated message. Recording a commit ID alone is not a reason to use it as the merge target. If the ref moved, merge the recorded commit ID and report why the name could no longer be used, preserving Git’s generated message. Don’t substitute the newer tip or fabricate branch provenance. An explicitly requested commit-ID merge still uses that commit as its target. For cherry-pick sequences, apply one source commit at a time. At the shared post-commit checks, verify expected parent relationships for every operation and that a merge result contains the recorded source commit.
