# Protected skill mutation

Use this policy for every authorized change within the project-authored public `human-facing-writing` source at `skills/human-facing-writing`, regardless of agent identity. For a project-authored immediate `.agents/skills/<skill>` tree, apply this policy only when your agent identity is Zed Agent. Running another agent inside Zed does not satisfy this condition. Every other agent must use its ordinary mutation workflow for `.agents/skills`.

A tree to which this policy applies is a protected skill tree. The policy covers each skill’s `SKILL.md`, assets, references, scripts, adjacent tests, and durable fixtures. Keep read-only work unstaged. Do not apply it to root `AGENTS.md`, `.agents/PROJECT.md`, other `.agents` paths outside `skills`, or any other root `skills/<skill>` tree.

The target checkout is the checkout containing the canonical protected skill tree. It may be the primary checkout or any linked worktree. Before selecting the staging host, run `git --no-pager worktree list --porcelain` in the target repository and use its registration records to classify the target checkout. Use the target checkout’s root as the staging host except when the target checkout is a registered `.agent-<name>` worktree. For that worktree, use the primary checkout’s root as the staging host so the worktree and staging root remain siblings rather than nested. The worktree’s `.agents/skills` tree remains canonical and is not a staged tree merely because its checkout root uses the `.agent-<name>` namespace.

Use the staging workflow below when native file tools expose both the canonical protected skill tree and the staging host through current project roots. Zed’s native mutation tools force confirmation for a directly named or canonical path containing consecutive `.agents` and `skills` components. Staging preserves the canonical layout required for project discovery without bypassing that confirmation boundary. The `skills/human-facing-writing` source uses the same staging and reviewed-promotion boundary for every agent because changes to its writing contract can affect every public skill composed through it, even though its path does not trigger Zed’s classification.

When this policy applies to `skills/human-facing-writing` and either required path is not exposed through current project roots, relay the change to an agent for whom both are exposed or stop. Do not mutate `skills/human-facing-writing` through the guarded direct route.

When this policy applies to `.agents/skills` and the canonical tree is exposed but the staging host is not, relay the change to Zed Agent for whom both are exposed or stop. Do not select an alternate or nested staging host. This branch is intentionally stricter than the guarded direct route because the canonical tree remains within Zed’s native sensitive-path boundary while the required staging location is unavailable. A direct edit would bypass staging rather than serve as the outside-root fallback.

Use the guarded direct route only when an applicable `.agents/skills` canonical tree is not exposed through current project roots. Do not create staged copies for this route. It is limited to updates to existing regular-file contents that preserve every path, type, and mode. Additions, removals, renames, type changes, and mode changes require Zed Agent for whom both the canonical tree and required staging host are exposed so in-bounds staging can preserve them. For an authorized update, obtain scoped write access, recheck the target’s tracked state and exact canonical state—including its path, regular-file type, mode, and contents—immediately before mutation, apply the smallest guarded direct edit, and validate the canonical result in place. If scoped access or an exact guarded edit is unavailable, relay the task to Zed Agent for whom both required paths are exposed or stop.

Retain each target’s original state in memory before writing and immediately record its resulting path, type, mode, and contents after every attempted write. For a coordinated change, preflight every target before the first write. If a write or validation fails, restore an original only after confirming immediately before restoration that the current state still matches its recorded resulting state. Do not overwrite a diverged target. Stop and report the partial state.

- Create one task-specific `.agent-<name>` staging root at the selected staging host, outside every protected skill tree. For every affected skill, preserve one immutable copy-time baseline and one editable copy of the complete `<skill>` directory at `<staging>/baseline/<skill>` and `<staging>/editable/<skill>`. Do not recreate `.agents/skills` beneath the staging root. For a new skill, preserve an explicit empty baseline and build the complete work-in-progress skill only under `<staging>/editable/<skill>`. Do not create its canonical `.agents/skills/<skill>` directory until reviewed promotion because Zed can discover and expose a partial skill to concurrent agent sessions. For a deleted skill, preserve the complete baseline and an explicit empty editable result.
- When the reviewed change alters the contents of a single file and adds, removes, renames, or retypes no path, stage only that file at `<staging>/baseline/<skill>/<path>` and `<staging>/editable/<skill>/<path>`. Recheck that canonical file against its baseline immediately before promotion, write the reviewed contents to its canonical path alone, then verify that the file matches the reviewed result and that no sibling path changed. Stage the complete skill tree whenever the change spans files, changes any path, or depends on cross-file consistency, and use the complete-tree recheck and promotion rules below for every change that does not qualify.
- For an in-bounds staged change, populate the immutable baseline from the canonical skill through normal native authorization, then create the editable copy from that unprotected baseline. Do not use terminal mutation, ancestor-directory operations, symlink indirection, or alternate path names to evade native confirmation or this policy’s staging boundary.
- Make every iterative change within the editable skill tree. Run every focused check that can operate there, including applicable documentation, script, test, fixture, and human-facing copy validation. Because `.agent-*` staging roots are normally ignored, invoke ignore-aware formatters with an explicit override that includes the staged paths and verify that each intended file was matched. For Prettier checks beneath the staging root, pass `--ignore-path=/dev/null`. A successful zero-file check is not validation. Review the complete editable-tree diff against the immutable baseline before promotion.
- Recheck the status and diff of the canonical skill against the same baseline immediately before promotion. If the canonical tree changed after capture, keep the original baseline unchanged, capture one immutable snapshot of the new canonical state, and reconcile the original-baseline-to-editable task delta onto that snapshot with three-way semantics. Stop and report any unresolved conflict. Only after successful reconciliation, adopt the snapshot as the refreshed staged baseline, retain the reconciled editable tree, and review their complete diff. If the canonical tree changes again before promotion, stop and report rather than restarting the cycle or overwriting user or concurrent changes.
- For a change staged as a complete tree, carry each finalized editable skill tree back to the protected tree’s canonical location with exact-tree semantics as one bounded promotion unit. The canonical result must match the reviewed editable tree, including intentional deletions. Do not use an additive merge that can retain stale files. Accept the native sensitive-path confirmation when that location is under `.agents/skills`, and carry back only project-authored skill content—not scratch artifacts or build output.
    - If native directory copying refuses an existing canonical destination, use a same-shape content promotion only when the rechecked canonical and reviewed editable trees contain the same relative paths and path types and the task changes only regular-file contents. Apply every reviewed regular-file content change to its corresponding canonical path in one bounded native pass, then verify complete tree equality. If any path is added, removed, renamed, changes type, or changes mode, use an exact-tree replacement operation or stop when none is available.
- Verify the promoted canonical skill against the reviewed editable result, then remove both staged skill trees before repository-wide canonical validation can inspect duplicate sources. Keep only non-source evidence needed for the task. If correction is permitted, recreate one immutable baseline and one editable copy from the promoted canonical tree rather than retaining duplicate source trees through validation.
- Run the complete authoritative check set against the canonical tree in non-mutating check, dry-run, or inspection modes. Do not run a canonical validation mode that writes into the skill tree. If a required canonical-only check has no non-mutating mode, report the limitation rather than starting a write-and-promotion cycle. If validation discovers a staged duplicate, correct the validation setup and rerun once without treating that result as a skill failure or starting the corrective pass.
- Aggregate all canonical-only failures before correction. After the initial promotion, permit at most one corrective staged pass for canonical-only failures or path-dependent discrepancies, then perform one final promotion and rerun the complete authoritative check set. If validation still fails, the same discrepancy recurs, or another correction would be required, stop and report instead of cycling.
