# Documentation boundary checks

Use these checks when an agent-documentation change crosses routed or layered documentation surfaces. Apply the entrypoint’s canonical-definition and secondary-role principle, then inspect only the applicable boundaries:

- **Description and body:** Apply the entrypoint’s description-content limit in both directions. Keep behavioral defaults, validation, optional composition, and internal workflow in the body, and do not let the body merely paraphrase the description’s trigger or exclusion. For a public skill, apply the [entrypoint-introduction marketing rule](public-skill-portability.md#compose-the-entrypoint) before classifying introductory overlap with the description as redundant.
- **Agent documentation and human-facing writing:** `agent-documentation` owns meaning, normative force, authority, metadata, portability, links, context footprint, and every structure that carries scope, order, routing, or another behavioral distinction. `human-facing-writing` owns wording, reading path, cohesion, tone, prose conventions, and presentation-only changes to headings, paragraphs, lists, and local grouping. Apply the selected `human-facing-writing` route when choosing between paragraphs and lists. Preserve the agent-documentation contract when the workflows conflict.
- **Inbound routes and exclusions:** Before adding or retaining a description exclusion, search project-authored skills for explicit routes that compose the excluded skill or surface. When the broad skill remains independently useful, place domain-specific non-composition policy in the narrower workflow rather than excluding the domain from the broad skill.
- **Base skill and overlay:** Classify whether the overlay co-applies across the base skill’s complete trigger family or narrows that family, and whether every supported installation guarantees the base. For a co-applying overlay with a guaranteed base, state in the description that the overlay applies whenever the base applies, name the base by its stable frontmatter `name`, and add any overlay-only triggers or exclusions. Define the overlay’s added behavior in its body, keep an explicit entrypoint route to the base, and do not repeat the base description’s capability, trigger family, or exclusions. For a scope-narrowing overlay, preserve its narrower triggers and exclusions in the description, define its narrower capability in the body, and route to the base from the entrypoint only where their scopes overlap. Do not claim co-application beyond the narrower scope. When a supported installation does not guarantee the base, keep the overlay independently complete. For a public overlay, follow the [public skill portability contract](public-skill-portability.md), including its permitted capability and value framing, preserve standalone behavior, and make any base composition optional. In every branch, keep the base unaware of the overlay and keep any dependency one-way.
- **Entrypoint and reference:** A reference must not merely paraphrase its parent entrypoint’s applicability or routing. When maintaining `posix-shell-scripting`, keep code-block examples out of its `SKILL.md` because the skill’s two-space Prettier indentation override applies only to its references and would reindent the YAML frontmatter if extended to the entrypoint. Structure the surrounding guidance as a coherent routed reference instead of moving examples alone, and retain the governing rule and the reference’s activation condition in the entrypoint.
- **Generic and specialized workflows:** A specialized workflow must begin at its domain-specific divergence and route back to the generic lifecycle rather than repeating that lifecycle. A routed validation section inherits the parent workflow’s generic checks and lists only checks whose inputs, execution context, or observable result are specific to that surface. As an ownership test, remove each specialized rule’s domain-specific nouns and constraints. If the remaining instruction still applies to sibling routes, the parent entrypoint owns it. When the specialized copy is more complete, promote the complete rule before removing the duplicate.
- **Rule, procedure, and diagnostic:** A workflow may define a normative rule, a procedure may operationalize it, and a rubric may translate it into observable review evidence. Treat these as distinct roles when each secondary occurrence contributes only the action, sequencing, condition, or diagnostic needed at that surface. Shared terminology alone is not duplication. Treat a secondary occurrence as redundant when it restates the rule without adding a route-specific action, condition, or observation.
- **Shared decisions:** When two routed workflows affect the same output decision, the entrypoint must assign each workflow a distinct abstraction level and terminology. A specialized reference may constrain an inherited decision, but it must not claim the same term or level as another route. When a specialized layer changes only the representation of inherited semantic values, refer to the inherited category and define only the transformation. Do not repeat concrete values merely to demonstrate that transformation.
- **Global policy and skill:** A skill may name an always-loaded global policy but must not restate it unless a distinct surface-specific application is required. A public skill that may be installed without that policy may carry a standalone mirror under the [public skill portability contract](public-skill-portability.md).
- **Output contract and template:** A template must not restate directives already established by its output contract.
